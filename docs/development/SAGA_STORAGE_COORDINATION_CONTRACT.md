# Storage coordination and acknowledgement

Master-index mutations, direct replacements, initialization and integrity verification share a queue per backend identity and index path. Persisted verification reloads the current index inside the queue rather than writing a supplied snapshot. Domain payload/index replacement uses the same path coordinator and retains the prior file for rollback after master registration fails.

`createSagaFileApi` exposes `storageBackendIdentity`. The default identifies the current host/account session; multi-account or custom adapters must provide a stable identity shared by every adapter for one backend/account. Custom adapters without identity coordinate only when they share the adapter object. Separate identities remain independent.

When `navigator.locks.request` is available and the backend identity is a shared string, Saga also obtains a browser Web Lock for that backend/path. Cooperating tabs on the same origin therefore serialize their mutations. Transactions acquire the outbox first, then the domain path, then the master index; these are distinct lock names. `getSagaStorageCoordinationCapabilities` reports the process queue, browser lock and conditional-write capabilities explicitly.

An adapter may implement `writeJsonFileConditional(fileName, value, options)`. It must atomically enforce `expectedMissing` (create only if absent) or `expectedRevision` (replace only the specified current revision) while writing. It must reject with status 409/412 or return `{ok:false,code:'storage_changed'}` on conflict. Saga turns these into a `storage_changed` failure. The default SillyTavern upload route does **not** expose this capability. Without Web Locks or server conditional writes, the fallback coordinates only one JavaScript realm: separate tabs, devices or external writers can still race and lose updates. Web Locks do not coordinate other devices or clients that bypass Saga. Server preconditions remain necessary for those writers.

Write/delete adapters and registration results returning `false` or `{ok:false}` are failures. JSON writes read back and compare canonical JSON; rollback reads exact prior text when supported, otherwise prior JSON; garbage collection verifies absence. A successful upload acknowledgment with stale or corrupt contents fails these checks. Raster assets currently use existence verification and content-addressed filenames; the adapter does not expose a binary readback/hash contract.

Queued storage failures include a unique operation ID, owner, operation, recoverable request snapshot, error/code and retry flag. Unrelated successes cannot clear them. A retry acknowledges only matching failures observed before enqueue; a same-owner operation already queued when another fails cannot acknowledge that failure. The durable journal uses the same captured IDs as the in-memory ledger. Flush returns `ok:false` while any retained failure remains. Verified rollback establishes a retry revision without disabling genuine external revision checks.

Library payload/owning-index writes, Creator projects, Story sessions, Theme Packs and Icon Sets use `/user/files/saga-storage-outbox.v1.json`. The prepared record includes the request and original file contents and is read back before canonical mutation. Payload contents are durable before their owning index is written. A committed journal record is read back before garbage collection or acknowledgment. Deletion removes the owning index record before deleting payloads/assets. Library layout/upsert/remove/import mutations merge only their own fields into the latest durable index; pending cache rows cannot be published by an unrelated layout save. Explicit full Library replacements validate referenced payloads.

Hydration recovers unfinished transactions from durable files: prepared/failed operations restore the prior complete version, while committed removals finish garbage collection. Failed requests remain in the outbox after verified rollback until an observed successful retry acknowledges them. Failed restoration or deletion retains the recovery record. Low-level domain primitives provide immediate rollback after registration failure; callers requiring crash recovery must use the transaction helper. The outbox gives recoverable ordered updates, not an atomic multi-file server transaction; a client bypassing coordination can observe intermediate contents. A backend refusing the prepared journal prevents canonical changes. A backend refusing every subsequent recovery write can prevent recovery progress, and failures before journal preparation cannot be made durable on that unavailable backend.

Sync store APIs return optimistic `{ok:true,queued:true,persisted:false,completion}`. Consumers must await `completion` and inspect its result before claiming external durability; `flush` also reports retained failures. Creator completion awaits a state-save result's `persistence` Promise and separately reports `metadataPersisted`. The legacy host metadata/settings scheduler may return void: external file acknowledgment is verifiable, host settings trimming and chat metadata disk persistence are not inferred from scheduling.

Startup calls `migrateSagaInlineStorage` before normal external hydration. Supported schema-1 or unversioned Library/Creator/Theme/Icon registries are preserved on ordinary settings reads/saves, with an exact raw recovery snapshot. Migration first writes and verifies `/user/files/saga-inline-settings-backup.v1.json`, then commits each payload and owning index. It compacts only after those acknowledgments. Durable source/canonical receipts make a completed migration idempotent when old settings reappear. Same-ID existing payloads without a matching receipt, changed canonical contents, divergent external organization, unsupported schemas, and unavailable persistence refuse migration with retained inline data and an actionable result. Migration creates only missing payloads, preserving a newly appearing external owner. A void settings scheduler yields `externalPersisted:true,settingsPersisted:false`; the verified backup remains available even if the trim is not saved.

Evidence: `test-saga-storage-reliability.mjs` reproduced ten initial failures and now passes 22 cases. `test-saga-storage-transactions.mjs` reproduced rollback/index/settings loss, stale upload acknowledgments, failed-payload layout contamination, default retry lockout, premature journal acknowledgment and borrowed coalesced completion receipts; all 28 cases pass. `test-saga-inline-settings-migration.mjs` covers refused/successful migration, all four newer external owner conflicts, repeated startup receipts, layout conflict, refused settings trimming and unsupported schema. Existing domain, master-index, stale-write, payload/library/Creator/Story, Theme/Icon and storage diagnostic tests pass. Full integrated release verification is recorded in the implementation ledger.
